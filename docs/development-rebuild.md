# Development database rebuild

Set `RETRO_DEVELOPMENT=true` and restart the application (Docker Compose forwards
this variable from `.env`). Open the settings cog and choose **Development:
rebuild database…**. Review the deletion notice, type `REBUILD`, and submit.
This feature is off by default; both management routes and the settings link are
absent unless enabled. Management authentication still applies. The POST requires
an unpredictable form token, exact confirmation, and the existing origin checks.
Do not enable it on a production instance.

The development policy intentionally permits deleting user data. The operation
removes saved/custom stations, registered radios and their names, assignments,
favourites, preferred audio choices, activity and music rotation history, all
catalogue/health/artwork caches, and podcast episodes. It preserves current app
settings and podcast feed subscriptions. Environment variables, API keys,
management credentials, discovery-helper configuration and manual UPnP source
URLs stay in place. It never deletes music or modifies the NAS/library server.

The operation cancels listening streams and drains all application HTTP work,
periodic discovery/feed work and detached UI cache/discovery workers before
changing the database. New work receives HTTP 503 with a retry hint. Concurrent
rebuilds are rejected. If draining fails, the database is untouched. After draining:

1. The normal `store.Open` migration and seed path creates a pristine temporary
   database. `SaveSettings` carries over current settings.
2. SQLite `VACUUM INTO` creates a consistent, private (0600) backup beside the
   live database, including committed WAL data. Its filename is logged as
   `retro-radio-before-rebuild-*.db`. Backup creation must succeed before reset.
3. A transaction replaces all application schema/data with the schema and seed
   rows generated by the current migration path. This removes obsolete tables,
   columns and mappings as well as old rows. Foreign-key and integrity checks
   run before commit. The existing database handle/file remain in use; no live
   SQLite file or WAL is unlinked. Failure rolls back the transaction.
4. Old queues, playback tokens, pinned providers, buffered playback status estimates,
   discovery results, UI enrichment
   state, podcast search results, directory mirror discovery and generated DJ
   welcomes/local research caches are discarded. Only hash-named generated
   welcome MP3s are removed from the configured welcome directory.
5. Feed identities are restored through `SavePodcast` and fetched through the
   normal subscription/parser path. UPnP uses fresh providers and normal
   discovery/root browsing. Radio-Browser uses the normal first-page search.
   Music remains browsed on demand: the application has no persistent music
   index, and does not crawl or copy the entire NAS during reset.

Source failures are reported on the result page. Offline podcast subscriptions
remain for normal hourly retry, without old episodes; music discovery retries
normally every 30 seconds. Radio catalogue pages and artwork populate when
browsed. This is a fresh internal database, not a bulk import of the worldwide
radio directory. Reopen music menus and reconnect listeners after completion.
Radios re-register on their next protocol request. Old saved device/station links
should be discarded; IDs from reset data are not durable across this operation.

Backups are not pruned automatically. To restore, stop the server, keep the
current database and any `-wal`/`-shm` files separately, copy the chosen backup to
the configured database path, and restart. Never overwrite a running SQLite
file. Reverting SQLite does not restore expired in-memory music sessions.

## Investigation findings

All eleven existing migrations were inspected. SQLite stores stations/variants,
radio selections, feeds/episodes, app settings, derived directory/artwork/health
caches, activity and last-play history. UPnP object mappings and programme queues
are in memory. Ordinary rediscovery deliberately retains providers and tokens,
so clearing SQLite alone could not invalidate stale music references.

The reported “PLAC” wording has no matching format or subsystem in this code.
The investigated path is UPnP album artwork, including FLAC music:

- Album containers had no artwork playback tokens; the browser UI therefore
  omitted their covers even if the server advertised `albumArtURI`.
- Relative artwork URIs were rejected by the scoped transport rather than
  resolved against the device description. They now resolve and must still pass
  the same pinned-server checks.
- A track without its own cover did not fall back to parent album artwork. Album
  children now inherit advertised artwork for display, and the image endpoint
  resolves the parent cover from fresh metadata. Folder artwork tokens cannot be
  resolved as audio. JPEG conversion, size limits and scope checks remain.

Agent FM already uses one ordered candidate snapshot, a zero-based selected
index and audio-timeline cues. Play All preserves the server's order and rejects
changed page totals/update IDs. The following gaps were fixed independently of
reset:

- Invalid presenter indices could retain speech while silently defaulting to
  candidate zero. Such links are now rejected before speech conversion.
- An announcement could enter the stream even if the chosen track had not yet
  opened successfully. The chosen decoder must now be ready before transition;
  a failed next resource ends the programme without announcing it.
- A server rescan could reuse an object ID while a queue retained its old title
  and artist. Agent playback now compares fresh title/artist/album and source
  resource identity with the announced snapshot, and requires reopening a changed
  station instead of playing the changed track under stale metadata.

These are reproducible code/fixture findings, not a confirmed diagnosis of the
user's particular NAS or radio. A server that supplies no artwork URI on either
track or album still has no artwork for this adapter to fetch. Embedded FLAC cover
extraction is not implemented. The physical radio's ability to refresh artwork
mid-stream is separate; Agent FM intentionally uses a fixed station logo.

Validation includes fresh-schema replacement, backups, repeat/reopen behaviour,
settings retention, cancellation, maintenance exclusion, production gating,
authentication/origin/token/confirmation rejection, normal source callback
repopulation, offline-source reporting, artwork inheritance/folder tokens,
provider/queue invalidation, invalid presenter indices and changed NAS metadata.
Real FFmpeg integration tests run only where FFmpeg is installed.
