# Architecture

Retro Radio Server is a local audio-content hub and compatibility layer for legacy radios. Internet radio, podcasts and UPnP music share hierarchical menus and compatible playback delivery, while source ownership remains separate.

## Components

- `cmd/retro-radio`: configuration, HTTP listener and CLI health check.
- `internal/protocol/frontierxml`: legacy directory requests, registration, favourites, search, metadata groups and station lookup.
- `internal/store`: SQLite persistence, migrations, stable identifiers, per-radio favourites, health records and bounded directory caches.
- `internal/catalogue`: Radio-Browser mirror discovery, filtering, failover and cached candidate resolution.
- `internal/content`: small source-neutral `Provider` interface (`Browse` and `Resolve`), folders, playable items, paginated pages, source resources and playback decisions. Existing radio/podcast persistence is unchanged; the abstraction is introduced at the alternative-content boundary rather than rewriting proven paths.
- `internal/upnp`: bounded ContentDirectory description/Browse client, resource selection, opaque LAN relay/artwork, and optional SSDP candidate discovery.
- `internal/artwork`: shared bounded conversion to the existing 128-pixel radio JPEG.
- `internal/podcast`: bounded RSS/Atom parsing, cached Apple search and hourly feed refresh.
- `internal/delivery`: checked upstream connections, live probes, HTTP relays and adaptive audio conversion.
- `internal/web`: authenticated management routes, Go templates, progressive discovery and bundled HTMX.

One Go process serves both the radio protocol and the management interface. The Docker image includes FFmpeg and runs as UID/GID 10001. SQLite is held in a persistent volume. The application listens on port 8080 by default; Compose exposes port 80 for legacy radios.

## Library and radios

All saved stations are available on every radio. Favourites belong to a radio/station pair. Older assignment records do not restrict shared-library visibility. Country and genre groups come from station metadata, with an uncategorised group for missing values.

Stations have numeric directory IDs and random opaque playback IDs. A monotonic counter prevents a deleted directory ID from being reused for a different station. Editing a custom station preserves identifiers and clears stale health when its listening link changes. Removal deletes its library entry, associated favourites and health in one transaction.

Registration hashes the opaque protocol identifier. An incoming request identifies an adapter namespace, not an exact model. Human-readable radio names are separate from protocol metadata.

## Discovery and management

Radio-Browser mirrors use forward/reverse DNS discovery with fallback hosts. Searches combine name, country and tag filters, with 24 results per page and bounded offsets. Query results and candidates are cached separately from the library, retaining at most 128 searches and 2,000 candidates. Offline results are labelled in plain language.

Popular discovery caches background jobs by country and distinct-channel offset, up to eight jobs with bounded lifetimes. Checks run in batches of four; usable results are progressively rendered through HTMX, retaining ranking and returning up to 24 stations per page. Pagination retains exact channel cursors so skipped unavailable streams do not create gaps when returning to earlier pages. Each library addition performs its own live check before saving; a discovery check does not bypass admission.

A single Go template renders station cards across discovery, search, library and radio views. Context determines Add, Remove or favourite controls. The persistent shell loads page fragments, preserves normal URLs and supports non-HTMX forms. Destructive library actions use styled confirmations; result dialogs report additions. Technical activity remains available in the support report.

## Playback and upstream safety

Playback accepts stored opaque identifiers rather than arbitrary target URLs. Initial links, DNS answers and redirects reject loopback, private, link-local, metadata and other non-public addresses. Checked addresses are pinned for dialing while TLS hostname verification stays enabled. URL credentials and environment HTTP proxies are disallowed. Public ports 80, 443 and 1024–65535 are supported.

HTTP links are attempted over verified HTTPS first, falling back to the original HTTP origin when necessary. Explicit HTTPS links retain certificate checks. Compatible, recently checked HTTP streams may be played directly; other legacy-radio streams use a local HTTP relay. Direct-play health expires after one hour. The default profile allows MP3 and AAC over HTTP, including ICY metadata.

Streaming uses bounded buffers and connection/header/idle/write limits. Range requests and HTTP/1.0 clients are supported. Raw `ICY 200 OK` status lines and PLS playlists are not supported.

HLS and DASH are decoded by FFmpeg into continuous 128 kbps MP3, 44.1 kHz stereo. FFmpeg reads a temporary token-protected loopback gateway; remote manifests and segments still pass through the checked transport. Manifests are limited to 2 MiB and individual media responses to 32 MiB. Encrypted HLS and protected DASH are rejected. Up to four conversion processes run concurrently and stop on cancellation or disconnect.

## Authentication and scope

An optional management password protects the web interface, REST API and support report. Browser writes reject cross-origin submissions. Radio endpoints remain unauthenticated for compatibility. Directory identifiers are spoofable and playback IDs are bearer URLs: this is a trusted-LAN service, not a multi-tenant public proxy. Remote management requires operator-provided network protection.

Audio checks record timestamps, connection metadata and last success without downloading a whole stream. They establish receipt of audio, not physical-radio decoding. Later failures do not remove saved stations.

## Channels and audio alternatives

Schema 6 stores stream alternatives, UUID aliases, old preset/stream aliases and per-radio audio preferences. Existing stations are consolidated only when normalized name, country and website or stream host establish a match; language and programme distinctions are retained. Custom stations remain independent. Favourite membership is unioned when channels merge. The migration is transactional.

Catalogue pages assemble a bounded prefix of cached directory pages and group before applying UI offsets, so pages contain 24 distinct channels. Library admission probes up to 16 compatible alternatives, four at a time within 90 seconds, and saves only working playable streams. Playback checks capabilities, recent failures, direct/adaptive delivery and estimated codec/bitrate quality. Multi-stream channels always use the relay so startup failures can fall back before headers/audio are committed. Once playback starts, a change of codec requires reconnecting. Radio-specific overrides change the first attempted stream, retaining fallback.

## Podcasts

Schema 7 adds shared subscriptions and episode records without changing station or favourite data. A refresh atomically updates metadata and matches episodes by publisher GUID (falling back to enclosure URL), preserving IDs. It accepts up to 200 public MP3/AAC episodes per feed and retains at most 500 recent episodes. Feed failures preserve existing data. Deleting a subscription cascades to its episodes; a refresh cannot recreate a removed subscription.

Feeds have an 8 MiB limit and a 20-second deadline, and use the same DNS-pinned, public-address-only client as streams. XML external entities are not expanded. Audio enclosure URLs are validated before saving and checked again through the playback transport. Podcast search uses Apple’s public search endpoint with 24 results, a bounded 15-minute cache and a 15-second deadline. No remote artwork is loaded. Episode playback uses the existing bounded relay, HTTP/HTTPS negotiation, GET/HEAD and Range support. `/episode/<id>` accepts stored identifiers only, and is accessible to radios without management authentication. Subscription and episode IDs can be guessed; this remains a trusted-LAN service.

### Radio dashboard

Schema 8 adds a station artwork link and backfills cached directory artwork without changing radio or favourite membership. Artwork is fetched by saved station ID through a public-address-only, redirect-checked client with an eight-second deadline and 1 MiB limit; executable image formats are excluded. Older library entries can retrieve missing artwork lazily from Radio-Browser.

The dashboard refreshes radio cards every five seconds. Each card shows favourite count and either the last radio contact or active station, listening duration, artwork, codec/bitrate and broadcaster-supplied song/genre information where available. Protocol playback links carry a radio ID; older links can be attributed by an unambiguous known radio address. Web playback is excluded from radio status. Direct ICY stream metadata is observed without changing forwarded bytes; BBC adaptive conversion does not currently supply track information. Unknown or ambiguous clients do not claim a radio card. A connected stream confirms delivery, not the radio's volume or audible speaker output.

Station cards use the same artwork proxy and a fixed music-note placeholder for missing or failed images. Directory candidates are addressed by cached UUID, never arbitrary image URLs. Original stations without directory IDs resolve artwork from a matching cached channel, exact directory stream URL, or the same named channel and country on sibling broadcaster stream hosts; name-only matches are rejected. Regional audio channels remain separate even where branding is shared. HTTP artwork links are tried over HTTPS first. The lookup changes only artwork metadata, preserving station IDs, streams and favourites. Images load independently of page fragments and remain stable during HTMX refreshes.


## My Music and UPnP ContentDirectory

`upnp.Manager` is the My Music root and aggregates up to 16 automatically discovered music servers, plus an optional `RETRO_MUSIC_SERVER_URL` administrator fallback. Each server uses the existing provider with independent opaque IDs and pinned transport. The provider lazily fetches its UPnP description, locates a standard ContentDirectory service (including embedded devices), resolves `URLBase`/relative `controlURL`, then uses SOAP `Browse`. Initialization is serialized, retryable and bounded by the request context: no startup dependency on music availability. Successful configuration and address pinning are retained for the process lifetime; automatic discovery replaces changed advertised endpoints after fresh sender-bound validation; manually configured endpoints require restart after address changes.

The Pure root groups content into Radio, Podcasts and Music. Radio opens a submenu containing the existing station, country, genre, favourite and search views; their existing endpoint links remain valid. Back from those views returns to Radio, and Back from Radio returns to the top level. The former MyMusic link is retained for already-open menus. Manager object `0` lists discovered server folders; composite server-key/object-ID links route browsing to each server's own root `0`. No dummy extra MinimServer layer is inserted. No Artist/Album/Genre hierarchy is hard-coded. DIDL containers become established Frontier `Dir` items; audio entries become established `Station` list/lookup items. Music uses the same numeric StationId shape and Radio format as the working station catalogue. A bounded in-memory mapping (4,096 entries, 24-hour idle expiry) connects reserved numeric IDs to provider-issued opaque playback tokens; no library metadata or resource URLs are stored there. Older in-flight opaque IDs remain accepted. Music lookup success/failure is recorded without radio identity queries. No new Pure wire types or native-radio UPnP behaviour are claimed. Base64 URL encoding carries opaque UPnP object IDs safely through folder links; these identifiers select server objects, never arbitrary URLs. BrowseMetadata of the current container supplies its actual parent and title for backward navigation. Artist, album and duration come from DIDL and map to the established description field; `albumArtURI` becomes an opaque local logo link.

One-based Frontier `startItems`/`endItems` maps to zero-based UPnP `StartingIndex` and `RequestedCount`; `TotalMatches` is returned as the catalogue count. Default pages contain up to 24 entries, maximum 100, with a maximum offset of 1,000,000. `NumberReturned` is checked against decoded items and used for web next-page offsets. Web links retain a bounded history of actual cursors, so Back remains exact if a server returns fewer entries than requested. Mixed container/item order is preserved; unplayable or non-audio entries retain their positions with no compatible resource, so filtering cannot silently corrupt page offsets. The provider never fetches all children to construct a page. Nested browsing fetches only one requested page plus one container metadata record, inside an overall five-second deadline.

Selection uses all advertised `res` alternatives. HTTP-get MP3 (`audio/mpeg`, `audio/mp3`) and ADTS AAC MIME types are preferred for the owner-confirmed profile, with UPnP byte/second bitrate translated to kbps. If no compatible native resource exists, server-hosted FLAC (`audio/flac`, `audio/x-flac`) can use the MP3 conversion fallback. MP4/M4A and other formats remain unsupported. Codec compatibility and transport compatibility are separate: `RETRO_RADIO_HTTPS=true` explicitly enables the directory-request profile's HTTPS capability, while radio music playback always emits `/stream/upnp/<opaque-token>?radio=<known-device-id>` to retain attribution through reverse proxies. The web browser always previews through that relay. Plain HTTP is relayed even for HTTPS-capable radios so server-side redirects retain checks. Native resources retain source audio; the FLAC fallback emits the existing compatible MP3 profile.

Playback tokens contain 128 random bits and resolve only to browsed server object IDs. A bounded 4,096-entry memory registry reuses tokens for an object, expires idle records after 24 hours and evicts the oldest when full. Every resolve refetches BrowseMetadata and reselects a compatible scoped resource; no stale source URL is trusted merely because it was seen previously. IDs reset on process restart and there is no music SQLite migration, metadata mirror, NAS access or rebuild. Long-lived music presets/favourites are not implemented. Browse/update IDs are exposed by the internal page model; browse responses are currently not cached, avoiding invalidation complexity.

### Separate LAN transport boundary

The radio/podcast public-only delivery policy is unchanged. The UPnP provider has an opt-in transport restricted to the configured hostname and its initially resolved, pinned IP addresses. It permits source resources on other non-privileged ports on that server, covering separate UPnP/control/audio ports. Private LAN addresses are allowed explicitly here; loopback, link-local and non-unicast addresses are rejected. Credentials in URLs, fragments, environmental HTTP proxies, unsafe ports and resources/redirects to other hosts are rejected. Dialing uses only the checked pinned addresses, including redirects, with ordinary TLS hostname/certificate validation. URLBase and controlURL receive the same checks. Music playback always uses server-side transport pinning, including compatible native HTTPS audio.

SOAP/description XML is limited to 4 MiB, with five-second total browsing/metadata deadlines and no external-entity expansion. The relay has 16 shared music/audio-artwork slots, connection/header/TLS limits, bounded 32 KiB copying and 20-second read/write idle deadlines, and stops on cancellation/disconnect. GET/HEAD, Range/If-Range and relevant range/cache headers are forwarded. Music delivery excludes live-radio reconnect and buffering, preserving native file seeking and finite track boundaries. Converted tracks retain finite boundaries but cannot seek by source byte offsets. Failure is local to music: startup, health checks and other directory branches do not contact it.

`/artwork/upnp/<token>.jpg` resolves only browsed metadata, fetches albumArtURI through the scoped transport within eight seconds and a 1 MiB limit, then applies the shared image dimension/pixel limits and 128-pixel JPEG conversion. Missing/unsafe/malformed artwork fails independently of audio. It introduces no persistent artwork or music mirror. Public audio/artwork endpoints remain bearer URLs because legacy radios cannot supply management credentials.

The authenticated HTMX Music page opens with available servers as clickable folders, then shows the server hierarchy with Back navigation, 24-entry pages, track playback with full-width native audio controls, artist/album/duration beside the artwork and brief failure feedback. Discovery controls and format explanations are kept out of the interface; the dashboard uses the shared Music menu without a duplicate setup card. Its root refreshes every five seconds so discovered servers appear without an extra user action. Radio dashboard polling still does not contact the music servers.

### Automatic discovery and Linux Docker boundary

The manager discovers at startup and every 30 seconds, with a 12-second total refresh deadline and four concurrent, five-second description validations. SSDP M-SEARCH asks for both standard MediaServer and ContentDirectory targets on up to eight active multicast-capable IPv4 interfaces. Each search is bounded to two seconds, 128 datagrams and 16 unique description links. Server keys use the UUID portion of USN, avoiding duplicates across service/device advertisements. Existing providers and playback tokens survive ordinary rediscovery. Brief missing announcements are retained; servers unseen for five minutes expire, while failed discovery operations do not erase the existing list. Manual fallback entries do not expire.

An automatically discovered description must resolve exclusively to the IP address that sent the SSDP response. The provider verifies this before fetching the description, pins that address and applies the same per-server control/resource/artwork and redirect checks. Multicast cannot supply an arbitrary destination for the LAN proxy. The validated friendlyName becomes the server folder title. New/changed endpoints are validated before publication. There is no library scan or metadata mirror.

Linux Compose retains the application's bridge network and HTTP port mapping. A second instance of the same image runs only `-upnp-discovery-helper` with `network_mode: host`, the existing non-root UID, a read-only root filesystem and all capabilities dropped. It opens UDP discovery sockets only, with no HTTP listener, database access or published port. This places SSDP on the actual LAN without altering the radio listener or requiring an address/port setting from users.

The helper writes a versioned JSON discovery handoff atomically in a dedicated volume owned by UID 10001. The application mounts it read-only. It contains at most 16 description links, USNs and observed source IPs, with a 64 KiB read limit and 90-second freshness check. It has no catalogue/library records, audio or persistent provider/playback identifiers. The manager still validates the source-bound description before connecting. A missing, malformed or stale handoff falls back to direct discovery. Docker Desktop's VM/layer-four host networking does not guarantee LAN multicast; native development on the Mac/Windows host or an operator-provided LAN deployment is required for reliable automatic discovery there. No router Internet port mapping is requested.


### Responsibility and format limits

MinimServer owns music scanning, metadata, organisation, search/indexing, source serving and any supported upstream transcoding. Retro Radio owns source aggregation, menu translation, capability/resource selection, legacy HTTP/TLS compatibility, scoped proxies and artwork normalization. Further providers can use the small content interface without becoming stations in SQLite. A future conversion decision can extend resource selection/playback without changing browsing.

MinimStreamer was investigated before adding music conversion. Its [official guide](https://minimstreamer.com/userguide.html) describes `stream.transcode` and resource URLs containing conversion settings; documented local FLAC outputs are PCM/WAV rather than a guaranteed MP3 output. Native compatible resources from MinimServer still take priority. WAV/FLAC decoding on the Pure is unverified, so the fallback converts source FLAC to the confirmed MP3 profile instead of claiming those capabilities.

### FLAC fallback

`RETRO_MUSIC_TRANSCODE` defaults to true. Resource selection uses FLAC only after exhausting compatible native MP3/AAC resources, and only when FFmpeg is found at startup, HTTP and MP3 are supported, conversion is enabled and the source URL passes the same server scope. The playback object records source resource and conversion separately; the wire adapter advertises the resulting MP3 codec and 128 kbps bitrate, and never gives the radio a raw FLAC direct URL. Web entries show FLAC → MP3 for that route.

The provider fetches source bytes through its checked LAN transport, forces FFmpeg's FLAC demuxer on `pipe:0`, restricts its protocol whitelist to `pipe`, and uses the existing 128 kbps/44.1 kHz/stereo `libmp3lame` profile on `pipe:1`. FFmpeg receives no server URL, playlist, NAS path or filesystem music file; no converted file is stored. Pipes and bounded copying prevent whole-track buffering. There are four music conversion slots in addition to the existing radio adaptive-stream slots. Process context cancellation, closed pipes/source bodies and a bounded process wait release slots on failure/disconnect. Output must contain at least 4 KiB within the startup deadline before successful audio headers are committed.

Converted responses advertise `audio/mpeg`, no Content-Length and `Accept-Ranges: none`. HEAD advertises that representation without starting a process. Initial `bytes=0-` requests restart at zero and receive 200; other byte ranges return 416 because FLAC byte offsets cannot describe MP3 output offsets. Native resources retain ordinary range forwarding. Transcoded seeking, album auto-advance and audible physical-Pure acceptance remain open. Generated FLAC → served MP3 → decoded PCM tests exercise the real encoder when FFmpeg is present, alongside mocked source/process lifecycle and failure tests.

Web navigation uses a shared Back-link template before the page heading. A central HTMX handler distinguishes user-triggered GET navigation into `#content` from timer updates and in-place mutations. Successful navigation scrolls to the window top and focuses the main content with `preventScroll`; explicit Back links and browser history restore remembered positions. Scroll memory is bounded to 100 URLs and independent of the disabled HTMX history cache, preserving fresh opaque playback tokens. `scripts/check-web-navigation.cjs` exercises this policy against the actual bundled scripts using Playwright WebKit.

Automatic source validation includes a bounded `BrowseDirectChildren` request for one entry at root `0`. Only a positive TotalMatches publishes an automatically discovered source; this excludes empty ContentDirectory services on renderers such as Evo One without filtering by product name. Empty roots remove existing automatic sources, newly populated roots appear on subsequent discovery, and transport/SOAP failures retain the existing five-minute grace period. Manual sources retain their explicit administrator configuration.

Station, podcast and music playback share `delivery.Relay` status tracking. Music providers notify a configured observer only after successful audio-byte writes; native and converted streams report the output codec, bitrate, title, artist/album and opaque artwork route. HEAD, failed lookups and artwork requests cannot start music playback status. Podcast episodes attach their ID, title, show title and supplied duration to relay context. Music directory links carry a validated radio ID; web players explicitly use `listener=web`. Existing radio attribution rules remain shared and never trust forwarded IP headers.

Finite radio playback with a known duration retains its latest active record after successful download completion until the estimated finish time, bounded to 24 hours. The next selection replaces buffered finite status for that radio; failed or interrupted transfers remove their own record, and expiry is checked when reading active status. Unknown-duration streams remain connection-based. The server cannot observe a device-local stop after full buffering. No persistent music metadata database or device control protocol is introduced.
